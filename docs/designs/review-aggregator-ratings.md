## Problem Statement

`/pelicula/<slug>` tells you what a film is and where to catch it in Buenos
Aires. It does not link out to the places a cinephile goes next. Afiche already
stores `films.tmdb_id` and `films.imdb_id` on every enrichment
(`src/tmdb/enrich.ts:585-604`), and the founding 2026-04-19 design doc banked
the IMDb cross-reference explicitly "so external links can be added later if
wanted."

Later is now. v1 is that, and only that: two outbound links, derived from
identifiers already on the row.

The operator's framing, verbatim: ratings should be **"a detail we showcase
and not the main piece of information we provide."** v1 takes the further step
of showing no figure at all and letting the destination carry it.

## What Makes This Cool

It is the smallest possible version of the idea and it costs nothing to run.
No table, no migration, no scheduled job, no third-party fetching, nothing that
can break, go stale, or be blocked. Two links whose correctness is exactly the
correctness of the poster and title already on the page, because they derive
from the same identifiers.

It also leaves Afiche's claim intact. Letterboxd tells you what people thought;
Afiche tells you it plays Saturday at Lugones at 23:00 and Wednesday at 20:00
at MALBA. v1 sends you to the first without pretending to be it.

## Scope — what was cut and why

Everything that involved acquiring somebody else's data.

- **Letterboxd rating figures: cut.** Operator, after an outside-model
  challenge: *"Ship only the links to the respective url for the movie on each
  site. Forget about the review score. Let's make that the simple v1."* This
  removes the `external_ratings` table, its migration, the fetch job, the
  cadence guard, the staleness window, the sample floor, the status vocabulary,
  the retention prune, the block detector and the golden-corpus fixture.
- **The Letterboxd Terms of Use problem: dissolved.** Their prohibition is on
  employing a robot, spider or scraper to access the Service. v1 performs no
  automated access whatsoever. A person clicking a hyperlink is the Service's
  intended use. (Codex argued the same clause's mention of "deep-link" reaches
  ordinary hyperlinks too; that reading is available but strained, since the
  clause governs automated data-gathering *tools*. Moot either way: nothing in
  v1 fetches.)
- **IMDb ratings: cut** (already, in revision 5). The only free source is a
  30 MB / 1,711,900-row dump to maintain roughly seventy numbers. Operator:
  *"It's an horrendous use case."*
- **Rotten Tomatoes: cut.** No identifier bridge from `tmdb_id` or `imdb_id`,
  so it would need title-and-year fuzzy matching.
- **`films.vote_average`: still never rendered.** Median six votes across the
  live catalog. See Premise 2.
- **Cartelera cards: out of scope.** This is a detail on the detail page.

**The April exclusion needs no reversal.** The 2026-04-25 doc's rule — *"NO star
ratings (we don't track them; never imitate Letterboxd's posture)"* — remains
literally true under v1, and so does `TODOS.md:722` ("Letterboxd shows ratings
(we don't)"). Neither DESIGN.md nor TODO #12 needs editing. Revisions 1-5
planned an amendment; v1 does not need one.

## Measured Evidence (retained for a possible v2)

Live catalog = 113 films with an upcoming screening and `hidden_at IS NULL`,
measured 2026-09-08 against the prod DB and live probes.

**What v1 delivers:** 86 films carry a `tmdb_id` (Letterboxd link) and 75 carry
an `imdb_id` (IMDb link). The other 27 get one link or none — and the ones with
neither are mostly rows that should not be films at all (festival umbrella
programs, "¡Película sorpresa!", "CONVOCATORIA DE CORTOS").

**What a v2 would argue from,** if a score is ever wanted:

| source | films rated | % of live | median sample* | p25 sample* |
|---|---|---|---|---|
| Letterboxd | 67 | 59% | 5,877 | 1,722 |
| IMDb | 71 | 63% | 2,996 | 322 |
| TMDB (stored, never rendered) | 65 | 58% | 55 | 12 |

\* over each source's **rated** films only. Over all 113, TMDB's median is **6**.

On the 13 long-tail films IMDb rates under 500 votes, medians run **Letterboxd
1,142 · IMDb 120 · TMDB 4** — Letterboxd is the deepest source on exactly the
Argentine premieres Afiche exists to surface. That is the case for a v2, and the
reason it would be Letterboxd rather than anything else. It would also
re-open the Terms of Use question, which v1 closes.

`letterboxd.com/tmdb/<tmdb_id>/` 302-redirects to the canonical film page; all
86 TMDB-matched live films resolved with zero misses, because Letterboxd's own
footer credits "Film data from TMDB". That is what makes the link derivable.

## Constraints

- **DESIGN.md governs.** Four hues, zero gradients, tracked micro-caps (Geist
  Mono, 0.25em, uppercase) for metadata. Carmine already carries time, the hover
  tick, focus rings, the active date chip, indie cinema names and the poster
  offset shadow; this row uses ink-gray and ink only. No logos, no badges, no
  brand colours — an IMDb yellow or a Letterboxd green would be the first
  foreign hue on the page and would read as an ad.
- **es-AR voice.** Spanish-native UI copy.
- **No ASCII diagrams in code comments.** Operator rule, 2026-09-09: *"we should
  not add diagrams on code comments, never."* Overrides the gstack
  plan-eng-review default, which recommends the opposite. Prose only.
- **`/pelicula` is `noindex`** and `force-dynamic`. `rel="noopener noreferrer"`
  on outbound links.
- **Phone-first, 375px.**

## Premises

1. **A link is only as correct as the match behind it.** `match_source` can be
   `auto`, i.e. fuzzy-matched, not human-verified (`src/db/schema.ts`). A wrong
   match sends a user to the wrong film on Letterboxd. But that same wrong match
   already puts the wrong poster, director, year and synopsis on the page, so
   v1 adds no new class of error — it inherits the page's existing confidence.
   This is worth stating because revisions 1-5 claimed the identifiers were
   human-trusted, which Codex correctly flagged as untrue.
2. **`films.vote_average` is never rendered.** Median six votes. It does not
   rank the Destacados band either: `src/db/queries.ts` ranks that by
   `popularity` (6 of 7 slot rules — 707, 713, 741, 748, 755, 761) and by
   `voteCount` (the `clasico` slot at 722). `voteAverage` is a passthrough
   (186, 497, 1324) in no rank function. Its one live consumer is the MCP
   `get_film` tool — Open Question 1.
3. **No new state.** v1 adds no table, no migration, no job, no scheduled work
   and no third-party request. The identifiers it needs are already written on
   every enrichment.

## Approaches Considered

### Approach A: cache ratings from Letterboxd — cut
Revisions 1-5. A table, a fetch job chained into `scrape-cron.sh`, a staleness
window and a block detector, to put a figure on 59% of live films. Cut by the
operator after an outside-model challenge argued the machinery was
disproportionate to one saved click and the stop-if-blocked control inadequate.
Retained above as the v2 case.

### Approach B: links derived from stored identifiers — chosen
No acquisition, no storage, no schedule.

## Recommended Approach

**Approach B.** Two derived links, rendered from identifiers already on the row.

### Getting the identifiers to the page

This is the one non-obvious part, and revision 5 got it wrong.

`getUpcomingScreeningsByFilm` (`src/db/queries.ts:429`) does a slug lookup
selecting `{ id: films.id }`, then returns `rows[0].film` — built by
`fetchRowsCached`'s mapper, which carries no `tmdbId` or `imdbId`. Widening that
slug select does **not** surface the identifiers; the row is discarded. Revision
5 claimed it was "one line, no effect", which was false, and the return type is a
shared contract `src/mcp/tools.ts:318` also consumes.

**Fix:** add `tmdbId` and `imdbId` to the film mapper at `queries.ts:163-190`
and to the `ScreeningRow['film']` type at `queries.ts:55-80`. Two lines each.

Why this is safe where a join would not be: this adds two **columns to an
existing select**, not rows to a result set. The fan-out hazard that shapes this
file applies to joining a table with N rows per film onto `fetchRows`, which
would duplicate showtimes across all eight of its call sites (284, 355, 443,
627, 870, 888, 1030, 1040 — the homepage windows, `/cartelera`, `/sala`
agendas, the featured band and the JSON-LD). Extra scalar columns fan out
nothing. `toFilmDTO` (`src/mcp/format.ts:132`) picks its fields explicitly, so
the MCP contract is untouched and needs no test changes.

No second query, no `cache()` wrapper, no injected clock. All three were
artefacts of the ratings design and go away with it.

### Render

`FilmLinks` in `src/app/_components/`, mounted as the **last child of
`<header>`** in `src/app/pelicula/[slug]/page.tsx`, after the conditional genre
`<p>` and before the backdrop `<figure>`.

**Monotone marks, not words.** Shipped as the brands' marks drawn in
`currentColor`, so they inherit ink-gray and flip to carmine on hover and focus
like every other interactive element.

```
  «MULHOLLAND DRIVE»
  David Lynch · 2001 · EEUU · 147 min
  MISTERIO · SUSPENSO
  ●●●   [IMDb]
```

Two earlier passes were built and rejected against the live page:

1. **Tracked micro-caps** (`LETTERBOXD ↗ · IMDB ↗`) directly under the genre
   eyebrow. Same ink-gray micro-caps register as the row above it, so the two
   read as one repeated label strip and the header looked cluttered even though
   nothing in it was redundant. Operator caught it on sight.
2. **Italic serif** (`Ver en Letterboxd · IMDb`). Fixed the echo by borrowing a
   register the header already used (the «original title» line), but it was
   still a row of words for what is meant to be a quiet detail. Operator:
   *"it's still text clutter, only on a different typography."*
3. **Merging into the genre row** was measured and rejected separately: the
   combined line wraps at 375px even with only two genres, leaving a dangling
   separator and an ambiguous break between genres and links. Worse than either
   on the phone-first surface.

**On the marks.** Real brand colours are out — IMDb's `#F5C518` and Letterboxd's
orange/green/blue would be the only saturated hues on a deliberately 4-hue page
(DESIGN.md: "Restrained. 4 hues, 0 gradients") and they out-shout the film
title. This was rendered and confirmed, not assumed.

Monotone was initially argued against on the grounds that neither mark survives
it. That was half right, and the half that was wrong matters:

- **Letterboxd does survive, but only with compounding opacity.** Its identity
  lives in three colours; flattened to one solid tone the circles merge into an
  undifferentiated blob that reads as a bullet ornament. Drawn at `fillOpacity`
  0.55 the overlaps darken on their own, rebuilding the multiply behaviour of
  the real mark, and it stays legible as three distinct dots in a single hue.
  The sub-1 opacity is load-bearing, not decoration.
- **IMDb is a wordmark in a box,** so using the mark removes no text. It is
  drawn as an outline rather than a filled box: a solid box is the heaviest
  element in the header at this size, and hairline containers are already the
  system's idiom (Pill's `ghost` variant).

Mechanics:

- `https://letterboxd.com/tmdb/<tmdbId>/` and
  `https://www.imdb.com/title/<imdbId>/`, derived at render, never stored.
- Each mark renders only when its identifier exists. Both missing renders
  nothing — no mark, no separator, no empty line.
- The marks are `aria-hidden`, so each link's `aria-label` is its entire
  accessible name ("Ver «Mulholland Drive» en Letterboxd"). Without it the link
  would announce as its bare URL.
- `target="_blank"`, `rel="noopener noreferrer"`.
- Verified at 375px with both marks present and four genres above them: no
  horizontal overflow.

## Open Questions

1. **The MCP `get_film` tool publishes `vote_average` bare** — no source label,
   no count, on a value whose median sample is six votes.
   `src/mcp/format.ts:145` puts it in the `FilmDTO`; `src/mcp/tools.ts:78` pins
   it in `filmDetailSchema`, referenced once at `tools.ts:310`; `toFilmDTO` is
   called once, at `tools.ts:330`. `search_films` and `whats_on` declare their
   own inline schemas without it. Tests at `src/mcp/format.test.ts:88`,
   `tools.test.ts:37`, `server.test.ts:47`. Unrelated to v1 and on nobody's
   critical path; worth its own small PR.
2. **Stale `imdb_id` after a manual `tmdb_id` patch.** `imdb_id` is a separate
   denormalized column, so an operator repointing `tmdb_id` in Drizzle Studio
   without re-enriching leaves the old IMDb id — and now a visible wrong link.
   The admin action does not have this problem (it re-enriches via
   `enrichByTmdbId`), and Studio edits already leave poster and title stale too,
   so this is a pre-existing operator hazard v1 makes more visible rather than a
   new defect. Captured as a TODO rather than guarded in code.

## Success Criteria

1. Both links render on every live film carrying the matching identifier: 86
   for Letterboxd, 75 for IMDb on today's catalog.
2. A film with neither identifier renders no row at all — no label, no
   separator, no empty rule.
3. Adding the identifiers changes no row count anywhere: the homepage,
   `/cartelera`, `/sala/[id]`, the featured band and the JSON-LD return exactly
   the screenings they return today.
4. The MCP `get_film` output is byte-identical to today's.
5. *Non-regression guard, not new work:* `films.vote_average` still renders
   nowhere on the web surface.
6. At 375px the header block still reports `documentElement.scrollWidth <=
   innerWidth` with both links present.
